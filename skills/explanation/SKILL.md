# explanation

質問者が十分に理解できていない分野の質問に答え、質問者が自分で判断できるところまで理解を助ける。説明は1回の返答で出し切らず、質問者と対話しながら進める。

## このスキルで使う言葉

- 本質問：質問者が最初にした質問の本体。`/explanation` に続けて書かれた文（`$ARGUMENTS`）がこれに当たる
- 理解度：ある用語や概念を、質問者がどこまで分かっているか。質問者の申告で決める
- 重要度：本質問に答えるのに、その用語や概念がどれだけ欠かせないか。「高」と「低」の2つに分ける
- 概念の深さ：その用語や概念が、ほかの用語や概念を前提にしているかどうか。ほかの前提になる基本のものほど浅い
- 説明の段階：1つの用語や概念を説明するときの、浅い説明から深い説明までの段階。手順5で決める

概念の深さと説明の段階は別のものである。概念の深さは用語どうしを並べる順に使い、説明の段階は1つの用語の説明をどこまで進めるかに使う。

## 全体の流れ

1. 用語と概念を洗い出す
2. 重要度と概念の深さで並べる
3. 理解度を3つずつ聞く
4. 手順3を、聞く項目がなくなるまで繰り返す
5. 1つずつ説明する
6. 本質問に答える

手順1と2は内部の作業なので、結果を質問者に見せず、手順3から始める。

## どの手順でも守ること

- 1回の返答は短くし、質問者の返事を待ってから次に進む
- 用語は、使う前に説明する。表、例、選択肢の中でも、まだ説明していない用語を使わない
- 別の道具に同じ名前の用語があるときは、どちらの意味かを毎回書く。たとえば Ansible のタグと Zabbix のタグは、名前は同じだが別の機能である
- 見た目が似ている別のものは、違うものだと先に書く。設定ファイルのキー名と、コマンドに渡すオプションの値がその例である
- 「簡単に言うと」「ご存じのとおり」「ただ〜するだけ」と書かない（分からなかった質問者を突き放す言い方になる）
- 本質問がリポジトリ、PR、設定ファイルのような実物に関わるときは、説明の前に実物を読む。実物から読んだことと、一般的な知識とを書き分ける

## 手順1：用語と概念を洗い出す

- 本質問が書かれていなければ、何を知りたいかを質問者に聞く
- 本質問に答えるのに要る用語と概念を挙げる
- 本質問に出てくる語だけでなく、説明に使う予定の語も挙げる。説明に使う語も、質問者にとっては新しい語になりうる
- 別の道具の同じ名前の用語は、別の項目として挙げる
- 本質問が広すぎるときや、意味が二通り以上に取れるときは、洗い出す前に質問者に範囲を聞く。推測で進めない

## 手順2：重要度と概念の深さで並べる

各項目に、重要度と概念の深さを付ける。

- 重要度が高い：これが分からないと、本質問への答えが分からない
- 重要度が低い：分かると理解が深まるが、なくても本質問への答えは分かる
- 概念が浅い：ほかの項目を前提にせずに説明できる
- 概念が深い：ほかの項目を1つ以上前提にしないと説明できない

次の順に並べる。同じ組の中では、ほかの項目の前提になるものを先に置く。

1. 重要度が高く、浅いもの
2. 重要度が高く、深いもの
3. 重要度が低く、深いもの

重要度が低く浅いものは、理解度を聞く項目から外す。説明の途中で必要になったら、その場で短く説明する。

## 手順3：理解度を聞く

聞く前に、次の項目を外す。

- 理解済みとして記録してある項目（「理解済みの記録」の節を参照）
- この会話の中で、質問者が正しく使っていた項目

外した項目があれば、名前だけを1行で示し、聞いてほしい項目があれば言ってもらう。

手順2で並べた順に、1回に最大3つずつ聞く。各項目に、1〜2文の短い説明と選択肢を付ける。短い説明の中でも、まだ説明していない用語は使わない。

```
**1. <用語>**
<用語>とは、〜のことです。
- [ ] a. 全く知らない
- [ ] b. 聞いたことはある
- [ ] c. 使ったことがある
- [ ] d. 使い慣れている
- [ ] e. 説明できる
```

最後に、「1-b、2-a、3-c のように答えてください」と答え方を1行で添える。

選択肢は項目に合わせて変える。道具でない概念（設計の考え方など）には「使ったことがある」が合わないので、「仕組みを知っている」のような選択肢に置き換える。

## 手順4：聞く項目がなくなるまで繰り返す

手順2で並べた項目を最後まで聞き終えたら、手順5に進む。

## 手順5：1つずつ説明する

理解度が「説明できる」でない項目を、手順2で並べた順に説明する。

### 説明の段階

| 段階 | 説明すること |
|---|---|
| 1 | 具体例やたとえ |
| 2 | それが何で、なぜ必要か |
| 3 | どう動くか、ほかの部品とどうつながるか |
| 4 | 例外的な場合や、うまくいかないときの動き |

どの段階から始めるかは、理解度で決める。

| 理解度 | 始める段階 |
|---|---|
| 全く知らない | 1 |
| 聞いたことはある | 1 |
| 使ったことがある | 2 |
| 使い慣れている | 3 |

どの段階まで進めるかは、本質問に答えるのに要る深さで決める。すべての項目で段階4まで進める必要はない。それより深い話は、説明せずに名前だけを挙げ、聞きたければ聞いてもらう。

### 進め方

- 1回の返答で説明するのは、1つの項目の1つの段階だけにする
- 返答の冒頭に、いまどの項目のどの段階かを1行で示す（「2/4 <用語>：段階2」）
- 抽象的な説明より先に、具体例を出す
- 具体例には、教科書的な例より、質問者が扱っている実物を使う。リポジトリのファイル、設定ファイルの1行、コマンドの出力などである
- たとえは、質問者がすでに知っている分野から選ぶ。質問者の分野が分からなければ、日常のものにたとえる
- 予定していなかった用語が説明に必要になったら、本筋を止めてその用語を先に説明し、本筋に戻る
- 段階の終わりに「ここまで理解できましたか？」と聞き、質問者が理解できたと答えたら次の段階に進む

理解の確認は、質問者の申告だけで行う。理解していれば答えられる問いを出して答えさせることはしない。テキストの会話では答えが直前の説明に書いてあるので、答えさせても確認にならない。理解が足りなければ、次の段階か次の項目で分からなくなるので、そこで気づける。

### 分からないと言われたとき

- 同じ説明を繰り返さず、別の具体例やたとえで説明し直す
- 前の段階で「理解できた」と答えた質問者が、次の段階で分からなくなったときは、前の段階の説明のどこが足りなかったかを確かめてから説明し直す。前の段階で分かったつもりだったことと、つまずいた箇所との差を示すと、質問者は自分に何が足りなかったかに気づきやすい

## 手順6：本質問に答える

必要な項目を説明し終えたら、本質問に答える。答えの中では、手順5までに説明した用語と、質問者が理解済みの用語だけを使う。答えが長くなるときは、手順5と同じように区切り、返事を待ちながら進める。

## 理解済みの記録

次のどちらかに当たる項目を、理解済みとして記録する。

- 手順3で「説明できる」と答えた
- 手順5で、本質問に要る段階まで説明し、質問者が理解できたと答えた

記録先は、エージェントの記憶の仕組み（Claude Code の auto memory など）にする。項目の名前、理解した段階、日付を残す。記憶の仕組みがない環境では記録しない。

次の会話で、記録した項目は手順3で聞かない。記録した段階より深い説明が本質問に要るときは、記録した段階の次から説明する。
